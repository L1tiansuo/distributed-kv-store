## 2026-11-19 分布式 KV Store 课程作业（并行与分布）

**交付物**：src/(node.py Raft 节点、client.py、run.py 控制台服务、console.html)、experiments/(6 组实验+harness)、
results/*.json(全部实测数据)、report/分布式KV Store 课程报告.docx(20页)、ppt/分布式KV Store 讲解.pptx(20页,含讲稿备注)、
README.md、Dockerfile+compose、tools/(make_figures、md2docx、build_ppt)。

**定稿设计**：场景=银行余额/转账；3 节点单主复制(quorum=2/3)；选主用 mini-Raft(不做 pre-vote/快照/成员变更)；
读=read-index 线性读(另留 stale 脏读开关做对照)；转账=一条日志项原子改两账户(不用 2PC)；幂等表放状态机(随日志复制)；
5 账户各 1000，总额恒 5000。

**关键实测数**：单笔 4.1ms(其中 fsync 3.6ms)；选主 390–1075ms(均 582，第1轮1075是落后节点白拉票)；
重启追平 527–574ms；只挂 1 从节点 15/15 写成功 2.8ms；失去多数派 3005ms 后 timeout_unknown 且 commit 冻结；
quorum=1 时脑裂，恢复后"订单-001"消失；幂等 3 发 1 生效；fsync 开关 253.8 vs 1646.2 ops/s(并发1)、374 vs 4072(并发4)；
单 key 热点与多 key 无差别(360 vs 374)。

**踩过的坑(已修，报告第6节有记录)**：①waiters 按日志下标回填导致把 noop 结果当转账结果→改为绑定 entry 对象+截断时 abort；
②只有心跳才复制→有未复制日志立即发(100ms→4ms)；③meta 每200ms fsync 卡写路径→只 flush；
④client 每请求新建 TCP 导致压测数据失真→连接复用；⑤Windows SO_REUSEADDR 允许抢端口，新集群连到旧进程→改
SO_EXCLUSIVEADDRUSE + pid 文件清理；⑥分区接口给已死节点发命令抛异常→try/except + 400 校验。

**运行**：cd src && python run.py --fresh → http://127.0.0.1:8080 ；复现实验 python experiments/run_all.py。
