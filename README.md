# 分布式 KV Store —— 银行余额/转账场景

> 华南师范大学《并行与分布》课程报告作业
> 仓库地址：`https://github.com/<你的用户名>/distributed-kv-store` ← **提交前请换成你们自己的仓库地址**

一个 3 副本的 KV Store，用 Raft 风格的日志复制实现**线性一致**的读写，并针对"钱不能凭空多、也不能凭空少"这一个业务要求，把幂等、CAS、多数派提交这三件事做扎实。代码量约 1800 行 Python（含网页控制台），不依赖任何第三方库，`python run.py` 一条命令拉起集群，浏览器里点按钮就能杀节点、断网、注延迟。

```
┌──────────────────────────────────────────────────────────┐
│  client.py（客户端）  req_id 幂等 + 跟随 leader 重定向      │
└───────────────┬──────────────────────────────────────────┘
                │  JSON over TCP（长连接）
      ┌─────────▼──────────┐   AppendEntries   ┌──────────────┐
      │  node1  (leader)   │◄─────────────────►│  node2       │
      │  日志 + 状态机      │                   │  follower    │
      └─────────┬──────────┘                   └──────┬───────┘
                │        AppendEntries                │
                └──────────────►┌──────────────┐◄─────┘
                                │  node3       │
                                │  follower    │
                                └──────────────┘
      写：leader 追加日志 → 复制到多数派(2/3) → 提交 → 应用 → 回包
      读：leader 先拿多数派心跳确认"我还是 leader"，再返回本地已应用的值
```

## 一、为什么选这个场景

题目给了 8 个场景。我们选"银行余额服务"，理由很实际：

| 候选场景 | 为什么没选 |
|---|---|
| 购物车（CRDT） | 冲突合并写起来不难，但**很难在台上证明合对了**。老师一句"两端都加了同一个商品，你怎么保证不重复"就要现场解释半天 |
| 游戏排行榜 | 实现最轻，可是它答不上 quorum、线性读、版本比较这一串追问，等于把图 2 那页 PPT 让出去 |
| 配置中心 | 读多写少，但实验全是"推送延迟多少毫秒"，数字不直观 |
| **银行余额** | 有一条**能用数字说话的不变式**：5 个账户总额恒等于 5000。任何一次错误都会让这个数字变，藏不住 |

选它不是为了好听，是因为它**最容易自证正确**。报告里所有结论都落在两个可验证的量上：总余额是否恒为 5000、同一个 req_id 是否只生效一次。

## 二、需求拆解

把题目那一句"在特定业务负载、故障模型和一致性要求下设计 KV Store"拆成三条：

**1）业务负载**

- 5 个账户（A~E），初始各 1000，总余额 5000
- 写：转账（跨两个账户）、设置余额、CAS 条件更新
- 读：按账户查余额
- 读写比按 1:1 设计，写是主要矛盾（每笔写都要落盘并复制）

**2）一致性要求**

- 转账原子：要么两边都改，要么都不改
- 读线性一致：读到的必须是"此前已成功的写"之后的值，不能读旧值
- 分区时**允许拒绝写入**，但不允许两边各写各的（这是题目原文给的余地，我们用了）
- 重复请求只生效一次（客户端可能重发，网络可能重复投递）

**3）故障模型**

一个副本宕机、双向网络分区、消息重复/延迟/乱序、节点重启丢内存、磁盘写成功但响应丢失、时钟倒退、单 key 热点。这些在图 6 里列了 9 条，我们逐条做了实验，第 5 节有对照表。

## 三、设计决策（每条都写了"放弃了什么"）

| # | 决策 | 放弃了什么 | 理由 |
|---|---|---|---|
| 1 | **单主复制**，不做多主 | 多主能多地区低延迟写 | 银行场景要线性一致，多主必然要处理写冲突；单主把冲突从"设计问题"变成"根本不发生" |
| 2 | **quorum = 2/3** | 可用性（挂 2 个就不能写） | 挂 1 个仍可写；quorum=1 会脑裂，实验三给出了数据丢失的现场证据 |
| 3 | **一条日志项 = 一笔转账** | 单条日志不能太大（我们限制 ≤10 个账户） | 跨账户原子性由日志天然保证，**不需要两阶段提交**。这是整个设计里最省事的一步 |
| 4 | **幂等表放进状态机** | 内存表更省事 | 只在 leader 内存里去重，主一换就失效；放进状态机后它跟着日志复制，任何新主都认得这个 req_id |
| 5 | **read-index 线性读** | 吞吐（每次读要多一轮心跳确认） | 直接读 leader 本地值会读到旧值；read-index 用一次多数派确认换正确性，代价是 1 个 RTT |
| 6 | **用 (任期, 日志下标) 定序** | 没有全局时间戳 | 物理时钟会漂移、会被 NTP 拨回、虚拟机还能被暂停。时钟只用来打日志，不参与定序 |
| 7 | **不做分片** | 写吞吐上限（单主串行） | 5 个账户的数据量用不上分片；做了反而要额外处理跨分片转账。代价见实验六：单主约 370 ops/s 封顶 |
| 8 | **不做快照 / 成员变更 / pre-vote** | 启动慢、不能动态扩容、偶发多花一个选举超时 | 日志只有几百条，启动回放是毫秒级；这三样都是"规模上来才回本"的工程，写进来只会增加被问倒的面积 |

这几个"不做"是主动的取舍，不是没做完。第 8 节专门写了如果继续做会怎么改。

## 四、协议细节

### 4.1 选主

- 心跳 100ms，选举超时在 350~650ms 之间随机（必须远大于心跳，否则 follower 会误判 leader 已死）
- 投片条件两条：任期不小于自己、且**对方日志不比自己旧**（比较最后一条的任期，任期相同比下标）
- 得票过半数才能当 leader；当选后先追加一条 `noop`，把前任留下的"已复制到多数派但没提交"的日志一遍推进
- 任期和投票对象**立刻 fsync 到磁盘**，否则重启后可能同一个任期投两次票，选出两个 leader

### 4.2 日志复制与提交

leader 为每个 follower 维护 `next_index` 和 `match_index`。有未复制的日志就立刻发，不等心跳（这一条把写延迟从 ~100ms 降到 ~4ms，是实验里最明显的一次优化）。

follower 收到 AppendEntries 时按 `prev_index/prev_term` 做一致性检查：

- 自己的日志太短 → 拒绝，并回 `conflict_index` 让 leader 一次退到位（不用一条条退）
- 同下标但任期不同 → **截断自己的尾部**，再从冲突处追加
- 已经有同一条（任期和下标的都对得上）→ 直接忽略，这就是"消息重复发三次"不会写三遍的原因

提交条件：`commit_index = 多数派里最大的已复制下标`，且**只提交当前任期的日志**（Raft 的安全性要求，靠 noop 间接提交旧日志）。

### 4.3 线性一致读

```
客户端读 → leader 记下当前 commit_index 作为 target
        → 向所有 follower 发一轮心跳，收到多数派应答
        → 确认自己还是 leader、且 last_applied >= target
        → 返回本地值
```

如果拿不到多数派应答，就一直等到超时（3s）后返回 `timeout_read`，**绝不返回可能过期的值**。实验五 D 段里，同一个 key 在孤立的旧主上脏读返回 1000，线性读直接拒答，两者对比就是这一段的现场证明。

### 4.4 幂等

客户端每个写请求带一个 `req_id`（客户端 ID + 随机串）。服务端两层：

- **快路径**：leader 在已应用的幂等表里查到 req_id → 直接返回上次结果，日志都不增长
- **慢路径**：状态机在应用日志项时查表 → 命中就跳过执行、只回放结果

慢路径才是真正保证。因为快路径依赖 leader 内存，主一换就没了；慢路径那份表是**跟着日志复制**的，新主上任后照样认得。实验四 D 段：写成功 → 杀掉 leader → 换主后用同一个 req_id 重试，新主返回 `duplicate`，账户只扣了一次。

### 4.5 持久化

- `log.jsonl`：一条日志一行 JSON，追加写 + `fsync`
- `meta.json`：任期、投票对象、commit_index。任期和投票必须 fsync；commit_index 只是恢复提示，落后是安全的（恢复时少放几条，等 leader 重新提交即可），所以定时保存时**只 flush 不 fsync**
- 启动时先装载日志，再从 1 回放到 commit_index 重建状态机。崩溃时最后一行可能是半条 JSON，解析失败就丢弃——这是"节点重启后丢失内存状态"的答案

### 4.6 接口

| 类型 | 报文 | 说明 |
|---|---|---|
| 写 | `{"type":"client","op":"transfer","from":"A","to":"B","amount":100,"req_id":"..."}` | 跨账户转账，原子 |
| 写 | `{"type":"client","op":"set","key":"A","value":900,"req_id":"..."}` | 直接置值，版本号 +1 |
| 写 | `{"type":"client","op":"cas","key":"A","expect_version":3,"value":900,"req_id":"..."}` | 版本不符返回 `version_conflict` |
| 读 | `{"type":"client","op":"get","key":"A","consistency":"linearizable"}` | 线性一致；`stale` 则读本地已应用值（仅用于对照实验） |
| 运维 | `{"type":"status"}` / `{"type":"admin","cmd":"partition","block":[2,3]}` | 查状态 / 注入故障 |

## 五、实验

环境：Windows 11、Python 3.13、本机 3 个进程（127.0.0.1:7301-7303），全部走真实 TCP 与真实 `fsync`，非模拟。

复现：

```bash
cd experiments
python run_all.py          # 6 个实验全部跑一遍，结果写进 results/*.json
```

### 实验一：基础功能（`exp1_basic.py`）

| 指标 | 结果 |
|---|---|
| 启动到选出 leader | 0.002 s（进程起来时日志为空，第一个超时就当选） |
| 30 笔随机转账 | 30/30 成功，平均 **4.1 ms**/笔 |
| 总余额 | 5000 → 5000，守恒 |
| 三副本账本 | 完全一致 |
| CAS 用过期版本 | 被拒，`version_conflict`（期望 13，实际 14） |
| 两个客户端同时 CAS 同一版本 | 1 成功 / 1 失败，版本 15 → 16（状态机串行执行，不会两个都改成功） |
| 余额不足转账 999999 | 被拒，余额不变 |

### 实验二：副本宕机（`exp2_failover.py`）

连续 5 轮，每轮杀掉当前 leader：

| 轮次 | 被杀节点 | 新 leader | 选主耗时 |
|---|---|---|---|
| 1 | 1 | 2 | 1075 ms |
| 2 | 2 | 1 | 527 ms |
| 3 | 1 | 2 | 480 ms |
| 4 | 2 | 1 | 390 ms |
| 5 | 1 | 2 | 436 ms |

- 平均 **582 ms**，范围 390–1075 ms
- 第 1 轮那 1075 ms 的原因是：**落后的那个节点先超时了**，它的日志比对方少一条，拉票被拒，只能等下一个超时再来一轮。这是 Raft 的正常现象，也是我们没做 pre-vote 的代价（第 8 节）
- 每轮切换后立刻写入都成功，总余额始终 5000
- 重启被杀节点，**527–574 ms** 追平日志
- 只杀掉一个从节点：15 笔写全部成功，平均 2.8 ms，说明多数派还在就不影响可用性
- **追赶途中再宕机一次**（落后 152 条时第二次 kill）：重启后 850 ms 追平，三副本重新一致。日志复制是幂等的，断点续传即可，不会写重也不会写漏

### 实验三：quorum 到底管什么（`exp3_quorum.py`）

**A. 挂掉 2 个节点（失去多数派）**

- 写请求在 **3005 ms** 后返回 `timeout_unknown`
- leader 仍然自称 leader，但 `commit_index` 从 2 到 2 **一动不动**
- 总余额仍是 5000：写进日志了，但没提交，就不会应用

**B. 把 quorum 从 2 改成 1（对照组，`--quorum 1`）**

制造分区 `[3] | [1,2]`，两边各自选出 leader，两边都收下了写：

| 分区期间 | A 侧（节点 3） | B 侧（节点 1、2） |
|---|---|---|
| 写入 | A→B 200 成功，另写了一个 `订单-001` | D→E 300 成功 |
| 账本 | A=800, B=1200, 订单-001=1 | D=700, E=1300 |

恢复网络后，任期低的那一侧被覆盖：

- `订单-001` **消失**
- A 从 800 变回 1000，B 从 1200 变回 1000

**这两笔写客户端都收到了"成功"**。这就是 quorum 从 2 改成 1 失去的东西：容错和防脑裂。银行场景里这等于凭空吞掉一笔转账。

### 实验四：幂等（`exp4_idempotent.py`）

| 场景 | 结果 |
|---|---|
| 同一 req_id 连发 3 次 | 生效 **1** 次，日志只增长 **1** 条，A 从 1000 → 900 |
| 对照组：3 个不同 req_id | 生效 3 次，扣了 300（这就是客户端不做幂等的后果） |
| 响应在途中丢失（发完就断开连接） | 服务端已扣 70；同 req_id 重试返回 `duplicate`，最终只扣 70 |
| 写成功后立刻杀掉 leader，换主重试同一 req_id | 新主返回 `duplicate`，D 只扣一次 50 |

### 实验五：故障模型（`exp5_faults.py`）

| 故障 | 现象 | 数据结果 |
|---|---|---|
| leader 出站消息延迟 10 s | 客户端 **498 ms** 后收到 `not_leader` 并被指向新主 | 旧主那条未提交日志被新主截断丢弃；同 req_id 重试在新主执行一次；A 只扣 120，总额 5000 |
| 消息重复发送 3 次 | 写入成功 | 日志只增长 1 条（同任期同下标的日志项被忽略） |
| 系统时间倒退 60 s | 写入照常成功 | 任期不变、日志下标 5→6 单调递增，定序不依赖墙上时钟 |
| 分区后读旧值 | 孤主脏读返回 **1000**（旧值），新主上是 **700** | 同一 key 的线性读在孤主上 **3012 ms 后拒答**；恢复后 18 ms 追平 |

### 实验六：性能与代价（`exp6_perf.py`）

每组先热身 40 次，再测 200 次，取 3 轮中位数。

| 配置 | 吞吐 | P50 | P99 |
|---|---|---|---|
| fsync 开，并发 1 | 253.8 ops/s | 3.7 ms | 7.3 ms |
| fsync 开，并发 4 | 374.3 ops/s | 10.3 ms | 14.5 ms |
| fsync 开，并发 4，**单 key 热点** | 360.6 ops/s | 10.5 ms | 29.5 ms |
| fsync 关，并发 1 | 1646.2 ops/s | 0.3 ms | 0.6 ms |
| fsync 关，并发 4 | 4072.1 ops/s | 0.7 ms | 4.0 ms |

三条结论：

1. **每笔写要 fsync 一次，单并发下吞吐掉到 1/6.5**（253.8 vs 1646.2）。这就是"多数派持久化"的价格，付得值——不 fsync 的那一列，机器一断电，已经回给客户端"成功"的写入就没了。
2. 并发从 1 到 4 只涨了 48%（253.8 → 374.3），说明**瓶颈在 leader 的串行日志**，不在网络。加机器没用，得加分片。
3. **单 key 热点并没有更慢**（374.3 vs 360.6）。因为在单主结构里，所有写本来就在 leader 上排队，50 个 key 和 1 个 key 都是同一个队列。这句话反过来说更重要：**我们没法靠分片打散热点**，这是不做分片的直接代价。

## 七、我们踩过的坑

这一节是真实的调试记录，不是总结。

**坑 1：客户端拿到的是 noop 的结果。**
换主时，客户端那笔写在旧主上被截断，但同一个日志下标被新主的 `noop` 占用了。我们的等待队列是按**下标**索引的，于是 noop 一应用，就把 `{"ok":true,"noop":true}` 回给了那笔转账的客户端——客户端以为转账成功，钱没动。
修法：等待项绑定**日志项对象本身**，应用时比对是不是同一条；同时在截断和降级时把相关等待项标记作废，让客户端立刻收到失败去重试。这个 bug 恰好就是"版本比较代码删掉会怎样"的答案。

**坑 2：写延迟被心跳拖住了 100 ms。**
最初只有心跳才触发复制，一笔写要等到下一个 100 ms 心跳。改成"有未复制日志就立刻发"，平均延迟从 ~100 ms 降到 4 ms。

**坑 3：每 200 ms 一次的 meta 落盘卡住整个写路径。**
定时把 commit_index 存盘时做了 fsync，在 Windows 上这一下要几十毫秒，而它是在持锁状态下做的，于是约 10% 的写会莫名卡 60 ms。改成只 flush 不 fsync（commit_index 落后无害），p99 从 63 ms 降到 9 ms。

**坑 4：压测数字一度是假的。**
第一版客户端每个请求新建一条 TCP 连接，测出来"关掉 fsync 反而更慢"。原因是连接建立的开销盖过了落盘。改成连接复用才测出真实的 6.5 倍差距。教训：**测出来的数不对，先怀疑测量方法**。

## 八、不足与下一步

1. **没有 pre-vote**。落后的节点会先超时、白拉一轮票，代价是偶尔多花一个选举超时（实验二第 1 轮 1075 ms，其余四轮都在 390–530 ms）。加上 pre-vote 就能避免。
2. **没有快照**。日志无限增长，现在只有几百条无所谓，上万条就要做快照 + 日志压缩。
3. **没有成员变更**。扩缩容要停机改配置。
4. **没有分片**。写吞吐被单主锁死在 ~370 ops/s，热点 key 也无法打散。
5. **单机三进程**。三个进程挤在一台机器上，共享同一块磁盘，"磁盘故障"这类相关性故障测不出来。真机部署时应该跨机器、跨机架。
6. **客户端没有做批量提交**。leader 如果把多个写请求打包成一条日志项，吞吐还能上一个量级。

## 十一、答辩问答（预演）

**Q：这行版本比较代码删掉会怎样？**
A：删掉的是 `on_append_entries` 里的 `prev_term` 检查。后果是 follower 会接受"下标相同但任期不同"的日志，旧 leader 迟到的 AppendEntries 就能把新 leader 已提交的日志覆盖掉。在我们的场景里就是已经扣过的钱又变回去。

**Q：写入成功究竟表示多少个节点已保存？**
A：3 节点里 2 个（含 leader 自己），而且**两个都是 fsync 到磁盘的**。不是 3 个——第 3 个可能还没收到；也不是 1 个——那样 leader 一挂就丢。实验三 A 段：只活 1 个节点时写不进去，`commit_index` 停着不动。

**Q：哪段执行可以让客户端读到旧值？**
A：`client_read` 里 `consistency="stale"` 那条分支——直接取本地已应用的值，不确认自己还是不是 leader。实验五 D 段：孤立的旧主脏读返回 1000，而新主上已经是 700。默认走的是 read-index，不会出现这种情况。

**Q：如果 quorum 从 2 改成 1，会失去什么？**
A：失去容错和防脑裂。改成 1 之后 leader 自己写进日志就算提交，另一个节点挂了也照写。分区时两边各自有 leader、各自接受写，恢复后任期低的一侧被覆盖。实验三 B 段：`订单-001` 直接消失，客户端当时都收到了成功。

**Q：为什么不能只用物理时钟解决冲突？**
A：三个原因。一是会漂移，两台机器差几十毫秒很常见；二是会被 NTP 往回拨，我们实验里人为拨回 60 秒；三是虚拟机会被暂停。用时间戳做"最后写入者获胜"，时钟一乱就会出现"先写的覆盖后写的"。我们用 (任期, 日志下标) 定序，这两个量只增不减，且不依赖任何机器的钟。

**Q：刚才那次失败请求的 happens-before 关系是什么？**
A：以实验五 A 段为例：客户端发请求（事件 a）→ 旧主追加日志（b）→ 旧主没拿到多数派确认，客户端超时（c）→ 新主当选并截断那条日志（d）。a→b→c 是客户端视角的因果；b 和 d 之间没有因果——d 所在的任期更高，所以 b 被判无效。客户端用同一个 req_id 重试（e），e 在 d 之后，与 b 不构成"同一笔业务"，所以只会生效一次。

**Q：为什么用一条日志项做转账，不用两阶段提交？**
A：因为我们的复制日志本身就是事务日志。一条日志项在状态机里同时改两个账户，要么整条应用，要么整条不应用，原子性由"按顺序、确定性应用"保证。2PC 是给"多个独立分片/数据库"用的，我们没有分片，用不上，还会引入协调者宕机、锁悬挂这些新问题。

**Q：幂等表为什么放在状态机里，不放在 leader 内存里？**
A：放内存里主一换就丢，客户端重试会扣两次。放状态机里，它是随日志复制的，新主上任后照样认得。实验四 D 段就是这个场景：写成功 → 杀 leader → 换主重试 → 新主返回 duplicate。

**Q：为什么不干脆让客户端自己保证不重发？**
A：客户端控制不了"响应丢失"这件事。请求已经执行、响应在路上丢了，客户端只能重发，它无法知道到底成没成。所以幂等必须在服务端做。

**Q：你们的系统能扛多少写？**
A：本机三进程，fsync 开着，单并发 254 ops/s、四并发 374 ops/s，p99 在 22 ms 以内。瓶颈是 leader 的串行 fsync 日志，不是网络。要往上走有两条路：批量提交（把多个请求打包成一条日志项）或分片（但分片要处理跨片转账，我们没做）。

**Q：三个进程都在一台机器上，这算分布式吗？**
A：算分布式系统的**协议验证**，不算故障域隔离。我们验证的是协议正确性（选主、复制、提交、脑裂），这些和机器数量无关；但"整机断电"这种相关性故障测不出来。真部署要跨机器，这在我们"不足"一节里写了。

**Q：为什么不选 CRDT/多主？**
A：银行要求线性一致，多主必须处理写冲突，而"两个人在两台机器上同时改同一个余额"没有业务上合理的合并规则——总不能把两次扣款加起来。CRDT 适合购物车这种"加了就加上了"的场景。我们选单主，是把冲突消灭在发生之前。
